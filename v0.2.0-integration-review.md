## 3. Modül bazında değerlendirme

### 3.1 API, karar motoru ve veritabanı

**Alınacak:** Reçetede ürün/renk/boyut/kusur/hedef kutusu tanımı, ortak C#/Python karar fixture’ları, bilinmeyen/düşük güvenli durumların ele alınması, takip durum makinesi, gerçek ve simülasyon işaretleri, karar/geçmiş kaydı, salt okunur sorgularda `AsNoTracking`, sınırlı sayfalama, mantıksal ayırmanın donanım komutundan ayrılması.

Yeni tablolar `ProductRecipes`, `CalibrationProfiles`, `InspectionRecords`, `ProductTracks`, `DatasetSessions`. Migration yalnız bunları ve indekslerini ekliyor; mevcut tabloları yeniden oluşturmuyor. Tek aktif reçete/kalibrasyon için kısmi unique indeks var. Şema yükseltmesi bir eski ürün kaydıyla ayrıca doğrulandı; tüm gerçek üretim verileri için kapsamlı yedek/geri yükleme deneyi yapılmış değildir.

**Düzeltilecek:** Aktivasyon transaction’ı, fiziksel sınırların uygulanması, manuel/model kaynağının ayrılması, dataset doğrulama/tutarlılık, simülasyon sayımlarının ayrılması. Reçetenin sürüm numarası tutulması olumlu; fakat gelen Vision gözleminin hangi reçete sürümüyle üretildiğini API doğrulamıyor. Kimlik alanlarının çoğunda ilişkisel foreign key ve iş akışı eşzamanlılık belirteci yok; mevcut endpoint kontrolleri tek başına yarış durumlarını çözmüyor.

**Sınır:** `MANUAL_REVIEW → DECIDED` domain geçişi var; bunu operatörün kullanacağı bir çözüm endpoint’i/UI akışı yok. v0.2.0’da bu durum yalnız inceleme bekleyen kayıt olarak sunulmalı; “manuel inceleme süreci tamamlandı” denmemeli. Fiziksel ayırma sonraki sürümdür.

### 3.2 Dashboard

Kontrol odası, inceleme, analitik, sensör, ayırma, reçete, kalibrasyon, dataset, geçmiş ve diagnostik sayfaları alınmalı. Rol kontrolleri, API hata zarfı, token yenileme, SignalR ve mevcut acil durum bileşenleriyle birlikte korunmalı. Caddy’nin mevcut SPA fallback’i yeni adreslere uygun.

Dataset ekranı etiketleri reçeteden seçiyor, tek istek sürerken yinelenen kamera isteklerini engelliyor, görüntüleri kimlik doğrulamalı API üzerinden okuyor ve önizlemeyi doğrudan dataset görüntüsü saymıyor. Ancak API tarafındaki eksikler UI ile kapatılamaz. Oturumun başka istemcide durdurulması, polling hataları, eski yerel durumun baskın kalması ve başarısız yakalama senaryoları için ek test gerekir. Geçmiş/analitik gibi bazı ekranlarda polling hataları görünür biçimde gösterilmiyor.

Reçete ekranı görüntüleme/aktivasyon yapıyor; reçete oluşturma/düzenleme API’sinin tamamını UI sunmuyor. Bu sürümde API üzerinden yapılandırma kabul edilebilir, belge bunu açık söylemeli. Kalibrasyon ekranındaki kayıt seçeneklerinin hepsi çalışan görüntü düzeltmesi değildir.

### 3.3 Vision ve model yönetimi

Kare rollerinin ayrılması, hatalı still’de açık hata, açıkça işaretlenen isteğe bağlı preview fallback, RGB565 büyük endian çözümleme, deterministik karar, artifact yokken boş çıkarım, gerçek gecikme ancak inference gerçekleştiğinde raporlama ve backend adaptörleri alınmalı.

**Uçtan uca yol eksik:** Vision `/inspect` sonucu döndürüyor; `InspectionPublisher` yalnız testlerde kullanılıyor. Dashboard’daki “Manual inspection trigger” model çalıştırmıyor; operatörün yazdığı sınıf/renk/boyutu API’ye kaydediyor. Bu manuel işlev yanlış değil, fakat gerçek AI incelemesiyle karıştırılmamalı.

v0.2.0 için önerilen minimum tamamlamada tek bir yetkili API tetikleme akışı, sabit reçete/sürüm ve kalibrasyon anlık görüntüsüyle Vision’dan sonuç alıp API’de kaydetmeli. Aynı olay iki kez kaydedilmemeli; başarısız model/kamera isteği başarı diye saklanmamalı. Alternatif olarak bu bağlantı tamamlanana kadar AI tetikleme açıkça deneysel olarak sunulabilir; sürüm tanımı yalnız manuel gözlem/simülasyon/veri toplama prototipi olur. **Bu raporun önerisi bağlantının v0.2.0 öncesinde tamamlanmasıdır.**

Gerçek eğitilmiş model veya doğrulanmış accuracy/mAP bulunmuyor. Registry’de `metrics: null`, `status: untrained` doğru yaklaşım; bu metadata alınmalı. Classification/segmentation runtime desteği iddia edilmemeli: adaptörler esas olarak detection kutularını okuyor, class probabilities veya segmentation maskelerini uçtan uca işlemiyor.

### 3.4 Kamera

GC2145 için RGB565 yakalama/yazılımsal JPEG, preview ve still ayrımı, PSRAM yoksa sahte VGA üretmeme, tampon sahipliği, preview geri yükleme, küçük iç RAM parçalarıyla gönderim ve ölçüm araçları anlamlı geliştirmeler. Ancak **yayın sırasında yeni still servisinin çalışmasını engelleyen sunucu yapısı düzeltilmeden çalışan kamera özelliği olarak alınmamalı** (B01).

Normal ve TCP tanı açık build derleniyor. Bu; doğru renk, fiziksel sensör stabilitesi, VGA still, PSRAM, eşzamanlı istemciler veya 50 yakalama dayanıklılığını kanıtlamaz. Rapor için cihaza bağlanılmadı ve firmware yüklenmedi.

TCP tanı derleme bayrağı varsayılan kapalı; kaynak/testler geliştirici aracı olarak kalabilir. HTTP throughput tanı uçları ise aynı korumaya sahip değil; sürüm build’inden çıkarılmalı veya ayrıca varsayılan kapalı derleme bayrağına alınmalı.

### 3.5 Dataset ve eğitim hazırlığı

API’nin veri seti için tek otorite olması, manifestte SHA-256 ve kamera kaynağı bulunması, etiketlenmemiş görüntüye kutu uydurmaması, model dosyalarını Git dışında tutması alınmalı. Eğitim, export ve registry araçlarının eksik veri/artifact durumunda gerçek metrik üretmiş gibi davranmaması olumlu.

Ancak örneği silme ile doğrulama araçları birbiriyle uyumlu değil (B10); checksum kaydı doğrulayıcı tarafından karşılaştırılmıyor; farklı split’lere aynı görüntünün sızması engellenmiyor. Veri seti export’u reddedilen kayıtlarla yine başarı kodu dönebiliyor. Bu hatalar giderilmeden güvenilir eğitim seti üretimi vaat edilmemeli.

`SmartLine.Vision/src/dataset_session.py` ikinci bir dosya yazıcısı; canlı Vision başlangıcında kullanılmıyor ve API oturum otoritesiyle ayrı durum tutuyor. v0.2.0 kapsamına alınmamasını, ona bağlı tek testin uyarlanmasını öneriyorum. `training/configs/classify.yaml` ve `segment.yaml` sonraki sürüme bırakılmalı; detection konfigürasyonu ve eğitim hazırlığı kalmalı. Notebook’lar çıktısız ve çalıştırılmamış; gerçek GPU eğitim/export deneyi yapılmadı.

### 3.6 Dağıtım, CI ve dokümantasyon

Dataset named volume ve API kullanıcısına yazma yetkisi verilmesi, Vision’ın iç ağda API’ye erişmesi, production’da 8090 yayınlanmaması ve CI’daki yeni kontroller alınmalı.

Geliştirme overlay’i `8090:8090` ile tüm host arayüzlerine açılıyor; loopback’e sınırlandırılmalı. Örnek ortamda belgelenen `CAM_CAPTURE_URL` Compose’ta aktarılmıyor. Model mount/ortam değişkenleri ve timeout’lar ortak bir kurulum tarifine bağlanmalı. Production Compose model runtime mount’u sunmuyor; development overlay’i `MODEL_PATH` değerini boş bırakıyor.

README büyük ölçüde değiştirilmiş. Proje adı ve genel amaç değişikliği kapsam kararı olarak korunabilir; geliştiricinin işlemci/RAM bilgileri, kişisel bench ölçümleri, geçici teşhis anlatıları ve eski bağımsız repo dizini varsayımları kalıcı public README’den çıkarılmalı veya teknik tanı dokümanına taşınmalı. Model/donanım sınırlamaları ve mevcut güvenlik kurulum yönergeleri korunmalı. `CHANGELOG.md` hâlâ yalnız v0.1.0 içeriyor; v0.2.0 kaydı/tag/release hazırlığı bu dalda tamamlanmış değil.

## 4. Somut bulgular ve düzeltme şartları

### B01 — P1: Sürekli yayın, still ve durum isteklerini bloke eder

**Kanıt:** `SmartLine.Cam/src/main.cpp:493,515,717,756`; `camera_control.cpp:787`. Tek `httpd_start` var; `/stream` içinde bitmeyen senkron handler çalışıyor. Still/durum uçları aynı sunucuya kaydediliyor. Kamera mutex’ini bırakmak HTTP sunucusu task’ini serbest bırakmaz. Vision da sürekli bu MJPEG bağlantısını okuyor; ayrıca Dashboard ikinci stream istemcisi açıyor.

**Sonuç:** İlk stream açıkken `/capture`, `/capture/raw`, `/status` ve diğer stream istekleri işlenmek için bekler. Bu davranış mevcut tek sunuculu eski yayının üzerine still eklenmesiyle kritikleşmiş. Espressif’in server-task açıklaması bu çıkarımı destekler: [ESP-IDF HTTP Server](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32/api-reference/protocols/esp_http_server.html). **Statik olarak güçlü bulgu; kartta yeniden üretim bekliyor.**

**Gerekli:** Stream’i ayrı servis/task veya desteklenen asenkron handler yoluna ayır; still/durum servisinin yanıt verebildiğini ve birden fazla tüketici politikasını doğrula. `camera_smoke.py:71` akışı yayın öncesi/sonrası kısa bağlantılarla kontrol ediyor; aynı anda açık yayın tutmadığı için sorunu yakalamıyor. Kabul: Vision sürekli okurken ve Dashboard açıkken VGA still + status başarılı, yayın sonrasında sağlıklı; 50 yakalama koşusu ancak bundan sonra.

### B02 — P1: API’nin 3 saniyelik süresi Vision’ın fotoğraf süresinden kısa

**Kanıt:** `SmartLine.API/Program.cs:282`, `Features/Inspection/VisionGateway.cs:140`; `SmartLine.Vision/src/main.py:38`, `still_capture.py:121`. API `vision-capture` istemcisine 3 s verir; Vision raw için 30 s, başarısız olursa ayrıca JPEG için 30 s bekleyebilir. Reçete çağrısı/işleme de ek süre getirir.

**Sonuç:** Geçerli bir still sürerken API isteği kesilebilir; operatörün kamera capture akışı çalışmaz. Timeout/camera unreachable hataları için özel operasyonel yanıt eşlemesi de yok. **Statik.**

**Gerekli:** Tek toplam deadline/bütçe, uyumlu ve yapılandırılabilir istemci süreleri, iptal yayılımı ve anlaşılır 503/504 yanıtı. 3 s’yi biraz artırmak tek başına B01’i çözmez. Kabul: 3 saniyeden uzun ama bütçe içindeki mock kamera yanıtı saklanır; süreyi aşan istek kayıt/görüntü bırakmadan kontrollü hata verir.

### B03 — P1: Gerçek Vision incelemesi kalıcı iş akışına bağlı değil

**Kanıt:** `SmartLine.Vision/src/control_server.py:44,75,84`; `inspection_publisher.py:13`; `SmartLine.Dashboard/src/pages/InspectionPage.tsx:25`. Yayıncının uygulama içi çağrısı yok, yalnız testi var. `/inspect` yanıtı döndürülüyor; API kaydı veya UI tetikleyicisi yapılmıyor.

**Gerekli:** Yetkili bir tetikleme → seçilmiş kare → Vision gözlemi → API kararı/kaydı → SignalR/geçmiş akışını bağla. Domain kararını yeniden yazmak gerekmez. Aynı olay için tekrar denemelerde çift kayıt engeli ve başarısız inference senaryosu ekle. Donanım tetikleyici şart değil; manuel tetikleme v0.2.0 için yeterli. **Statik çağrı zinciri doğrulandı.**

### B04 — P1: Reçete değiştirmek modeli değiştirmiyor, sınıf adlarını değiştirebiliyor

**Kanıt:** `SmartLine.Vision/src/main.py:88` model yalnız başlangıçtaki `MODEL_PATH` ile oluşturuluyor; aktif API reçetesi bundan sonra okunuyor. `control_server.py:63` sadece `engine.class_names` listesini değiştiriyor. `inference.py` runtime’ı bu isimlerle çıktı sınıfına etiket veriyor. API’nin model kayıt doğrulama CLI’sini zorunlu kullandıran bir aktivasyon kontrolü yok.

**Sonuç:** Aynı ağırlık yeni reçetenin sınıflarıyla adlandırılabilir; `artifactFileName`/model sürümü değiştirmek çalışan ağırlığı güncellemez. Görünen reçete ile gerçek inference farklılaşır. **Statik.**

**Gerekli:** v0.2.0’da tek detection artifact’ını açıkça yükle, sınıf sırasını artifact sözleşmesinden al ve reçeteyle eşleşmeyi doğrula; uyuşmayan reçete/model aktivasyonunu reddet. Canlı model değiştirmeyi sonraya bırak; restart gereksinimini belgele. Model yüklü olmaması açık bir durum olarak kalabilir.

### B05 — P1: Kalibrasyon ve fiziksel sınırlar karar akışına tam bağlı değil

**Kanıt:** `SmartLine.Vision/src/main.py:117` context kalibrasyonu daima `None`; pipeline hesaplaması bu değeri kullanıyor. API yalnız ayırma zamanlaması için aktif kalibrasyonu okuyor (`InspectionWorkflow.cs:192,285`). Reçetedeki `CalibrationProfileId`, `PhysicalLimits.MaxWidthMm/MaxHeightMm/MinConfidenceToSort` karar motorunda kullanılmıyor. Modelde tanımlı olmak uygulandığı anlamına gelmiyor.

**Yeniden üretildi:** DemoBox’ta `maxWidthMm=1`, `minConfidenceToSort=0.99` ayarlanmasına rağmen `BOX_GREEN`, 50 mm ve güven 0.9 gözlemi **PASS** döndü. Bu, normal boyut sınıfı eşleştirmesinin fiziksel güvenlik sınırının yerine geçmediğini gösteriyor.

**Gerekli:** Karar motorlarında sınırları ortak fixture’larla uygula; ölçek kalibrasyonunu ilgili still çözünürlüğüyle eşleştir. Ölçüm eksikse fiziksel uygunluk iddiası üretme. Perspective/orientation/flip uygulaması tamamlanmayacaksa alanları deneysel olarak belirt ve çalışan ayar gibi sunma. Gerçek VL53L1X yüksekliği bu sürüm için gerekli değil.

### B06 — P2: Reçete/kalibrasyon aktivasyonu iki ayrı kayıt işlemi
