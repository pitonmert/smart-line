# Work deferred from v0.2.0

The planned v0.2.0 scope is recipe-driven inspection, product tracking, logical sorting, dataset collection, and detection training preparation. The API owns persistent inspection and dataset state; Vision supplies camera frames and model observations.

This document records release scope decisions for contributors and users. It is not a release announcement. The accepted implementation is integrated into `main` without publishing a release tag. The old AI branch is retired without an archive branch. Its original detailed history is not a retention requirement; the decisions and future acceptance criteria below are retained instead.

## Files excluded from the integration candidate

| File | Responsibility | Reason for exclusion | Direction for future work |
| --- | --- | --- | --- |
| `SmartLine.Vision/src/dataset_session.py` | Writes images, session metadata and manifest entries directly from Python. | A second dataset writer maintains state independently of the API's sessions, validation and database records. Two write authorities can disagree about which session is active or which captures exist. | Keep the API as the write authority. If an offline collector is needed, design an explicit import/synchronization protocol with stable sample IDs, checksums, label validation and duplicate handling. |
| `SmartLine.Vision/src/inspection_publisher.py` | Posts Vision observations to the API with device authentication. | The helper is not wired into the branch's application entry point. The selected integration flow has the API request a Vision observation and persist the decision. A parallel publishing path would need its own retry, provenance and duplicate-record rules. | Prefer API orchestration. Reintroduce a push adapter only for a concrete event source, using the same pinned recipe/calibration contracts, authenticated access and persistent idempotency guarantees. |
| `training/configs/classify.yaml` | Configures whole-image classification training. | The v0.2.0 runtime and export path focus on detection. A configuration file alone does not implement classification outputs, evaluation, API mapping or Dashboard behavior. | Add an end-to-end classification contract, a reviewed labeled dataset, runtime/export support and tests before enabling this task. |
| `training/configs/segment.yaml` | Reserves segmentation training settings. | Segmentation requires real mask annotations and mask-aware runtime/output handling. The configuration explicitly reserves future work; it is not evidence of a trained or supported segmentation pipeline. | Define the mask format and annotation workflow, then implement export, inference, geometry mapping, API persistence and visualization with tests. |

Excluding the first two helpers does not remove dataset collection or inspection persistence from v0.2.0. Those capabilities use the API-managed path. Classification and segmentation remain unsupported release tasks until their complete workflows are implemented.

## Other deferred behavior

These boundaries also apply to features embedded in otherwise accepted files.

| Area | Why it is deferred or restricted | Acceptance needed before enabling it |
| --- | --- | --- |
| VL53L1X arrival events and physical measurements | Hardware input and its calibration have not been integrated and verified. Placeholder or simulated readings must not appear as real sensor data. | Device integration, calibration, timestamps, failure handling and explicit separation of real and simulated measurements. |
| Servo/gate actuation and physical sorting | A logical destination or queue release does not prove that an actuator moved a product correctly. | A defined actuator protocol, interlocks, timing calibration, safe failure behavior and hardware acceptance tests. |
| Orientation, flip and perspective settings | Stored configuration fields do not by themselves apply image transformations. | Transform pixels and associated ROI/box coordinates consistently; verify calibration resolution and geometry in tests. |
| Continuous inference and automatic model replacement | The release uses explicit inspection events and a configured detection artifact. Model replacement adds resource, concurrency and compatibility concerns. | Defined scheduling/backpressure or an atomic model lifecycle, artifact validation, rollback and observable failure states. Model changes require a restart in the selected v0.2.0 approach. |
| Multiple products and detection-specific color/defect analysis | The current pipeline chooses one primary detection and uses the recipe ROI for color analysis. | Per-product association, per-box measurements, independent decisions and tracking tests. |
| Inspection boxes over live preview | A previous inspection can have a different timestamp, resolution and field of view from the current preview. Drawing its boxes over live video can misrepresent the result. | Show boxes on the exact inspected snapshot, or implement and test an explicit temporal/geometric mapping. The integration candidate suppresses stale result boxes on live preview. |
| Diagnostic endpoints and development network exposure | Throughput tools and direct control ports are development facilities. Default availability is not required for normal inspection. | Keep diagnostics opt-in and development host ports on loopback. Authenticate service calls and bound request size, duration and concurrency. Unsafe original settings are intentionally discarded; diagnostics remain opt-in. |
| Broad architecture changes | Moving the system coordinator into a new project or restructuring all layers would widen the integration beyond the release's functional work. | Evaluate the architecture separately after the integrated behavior is stable; preserve meaningful operation when optional modules are unavailable. |

## Continuing development

- Build each change around a complete feature, including directly related API, Vision, camera, Dashboard and training work. Do not restore obsolete helpers or unsupported behavior simply to preserve old files.
- Start new feature branches from the updated `main` contracts. Do not merge the retired AI branch back into active development.
- Keep manual observations, model outputs and simulations distinguishable. Missing models, calibration or hardware must produce explicit unavailable/unsupported states rather than invented results.
- Include relevant regression tests and document prerequisites, compatibility and operational limits. A passing mock test or firmware build does not establish physical-device or trained-model performance.
- Treat API database records and dataset files as one operational backup unit. An optional offline collector must not silently become a second authority over live session state.

No deadline is assigned to the deferred features by this document. Each can be reconsidered when its implementation and validation are complete. The two obsolete Python helpers are intentionally discarded: their responsibilities are covered by API-managed flows. Classification and segmentation must be implemented as complete features when needed; their old configuration stubs do not need to be retained.

## Hardware and model acceptance still required

Before claiming real-device or model readiness, validate camera colors, PSRAM behavior, VGA/raw dimensions, concurrent preview and still/status access, repeated capture stability and Wi-Fi recovery on the target hardware. Validate an actual reviewed artifact against its class order, model version, input geometry and export contract. Physical sorting and model accuracy require their own measured acceptance results.
